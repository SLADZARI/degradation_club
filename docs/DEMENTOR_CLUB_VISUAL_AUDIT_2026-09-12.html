AUDIT

Visual debt и Projects evolution связаны одной архитектурной задачей: публичная сущность должна иметь одного canonical owner, понятный lifecycle и отдельные access capabilities вместо случайных runtime-представлений.

01 / SUMMARY

Текущую чистку надо закончить. Projects — проектировать рядом, но внедрять отдельным Result.

2P0 visual/runtime findings
5+P1 ownership findings
4project families already in repo
1→1canonical entity → presentation owner

Идея Projects правильная, но Board не должен становиться вторым Projects CMS.

Публичный Projects должен стать каталогом самостоятельных миров клуба: игры, editorial/media, продукты/решения, исследования и проекты участников. При этом Board остаётся пространством активности и происхождения: участник публикует Artifact/idea, а после отдельного promotion/review появляется canonical Project. Уже после этого Board показывает Project projection, а не независимую копию.

ARCHITECTURE

Separate maturity, publication and access

«Концепт», «можно попробовать», «публичный лендинг» и «кто имеет право комментировать» — четыре разных измерения. Их нельзя хранить одним status.

Scope decision: эту спецификацию можно вести в том же audit/planning package, потому что она использует выводы ownership-аудита. Но её implementation не следует смешивать с текущим visual-tech-debt cleanup. Новый Project registry/access workflow потребует отдельного Decision/Result, schema/RLS review и release evidence.

3.4 / Member Project promotion flow

01MEMBER ARTIFACTidea / post / request
02INTERESTresponses / relations / evidence
03PROJECT CANDIDATEexplicit promotion request
04SCOPED REVIEWassigned Dementor / authority
05APPROVED PROJECTnew canonical PROJECT id
06PUBLIC LANDINGstable URL + publication policy
07BOARD PROJECTIONcanonical Project projected back
Главная поправка к исходной идее: Member не должен «создавать Project на Board» напрямую. По действующему канону он создаёт Artifact. Promotion — отдельное действие. Original Artifact остаётся как provenance, а новый canonical Project связывается с ним через типизированную relation (`RESULT_OF`, `CONTINUES`, либо отдельно утверждённое promotion relation). Это сохраняет историю и не превращает Board во второй CMS.

3.5 / `/projects/` — public register contract

REGISTER

Не grid-магазин

Desktop — scan-first Entity Register. Поля: ID, title, kind, factual stage, origin, access/action. Preview media опциональна и не содержит essential information.

Consistent with Entity Register grammar
FEATURE

Только фактический hero

Допускается один dominant featured Project, например `PLAYABLE NOW`, но только если такой playable build реально существует. Concept никогда не маскируется под release.

One dominant project feature per viewport
FILTER

Фильтры из реальных данных

Kind / maturity / origin появляются только когда набор проектов реально требует фильтрации. Status-фильтр не должен придумывать состояния, отсутствующие в canonical data.

No decorative taxonomy

3.8 / Proposed logical data contract

Project { id entityType: "project" slug title kind: game | editorial | media | product_solution | research_experiment | tool | other origin: club | member sourceStage // raw canonical project-local state presentationStage // concept | prototype | playable | live | archived publicationState // internal | public_landing | published | withdrawn summary publicUrl preview media[] relations { creator[] owner[] assignedDementor[] collaborator[] } access { landing: public experience: public | authenticated | member feedback: member | scoped collaboration: member | scoped } experience { state: none | prototype | playable | live routeOrUrl implementationRef } board { originArtifactId? projectionPolicy } review { status: none | requested | changes_requested | approved | rejected decisionRef? } provenance updatedAt }
Не утверждённая DB schema: это logical contract для дальнейшего Decision. Его нельзя молча превращать в таблицы/миграции. Текущий content/templates/project.json слишком мал для новых требований, но менять его надо только после фиксации authority и migration strategy.

3.9 / Auth & security boundary

SERVER

Play gate не CSS

Protected game/app route нельзя защищать только скрытой кнопкой. Session/capability проверяется server/API/RLS или короткоживущим signed handoff.

Direct URL guessing must fail closed
SCOPED

Role ≠ permission

Dementor не получает автоматический доступ ко всем Project admin/review actions. Review/owner/publisher — entity-scoped assignments.

Deny by default
BOUNDARY

Shared auth only

Если Project имеет отдельный app/repo, можно reuse identity/login. Но DC Project data и permissions остаются DC-scoped и не смешиваются с Modern Pilgrims project registry.

Shared identity ≠ shared product

04 / EXISTING AUDIT FINDINGS

Projects spec не отменяет текущие visual/runtime blockers.

P0

Merch entity set расходится

Static catalog и runtime mapping описывают разные наборы SKU.

Fix: explicit canonical SKU ids/manifest; deterministic fixture; exact visible entity count. Это тот же architectural pattern, который нельзя повторить в Projects.

P0

Merch runtime может вернуть technical price fallback

Null commercial values не должны превращаться в visitor-facing `PRICE / TBD`.

Fix: public presentation policy отдельно от internal data fields; commerce activation остаётся отдельным Result.

P1

Home Fuengirola сохраняет suppressed legacy CSS-owner

Текущая композиция работает, потому что route layer гасит старый owner.

Fix: guarded consolidation → удалить legacy owner после screenshot parity.

P1

Duplicate stylesheet / global runtime ownership

Home event stylesheet и route-specific relation/runtime behaviors нуждаются в одном load/owner contract.

Fix: route responsibility manifest, one load path, build-time relation markup где данные известны.

P1

Visual regression coverage всё ещё неравномерный

Home защищён сильнее других public surfaces.

Fix: stable-region screenshots + structural owner assertions + deterministic runtime fixtures. Projects с первой версии должны сразу войти в этот тройной QA-contract.

08 / DEFINITION OF DONE

Projects считается готовым не когда появились карточки, а когда publication/access/projection согласованы.

#Done condition
01Каждый public Project имеет canonical id, stable URL, provenance, kind, sourceStage, presentationStage и publicationState.
02Anonymous public landing работает без auth; protected experience fail-closed без authenticated session.
03Member-only feedback/collaboration server-authorized и не наследует generic Guest Board response accidentally.
04Member-originated Project проходит explicit Artifact → promotion/review → canonical Project flow.
05Dementor review scope explicit; role alone не даёт global approval/publish.
06Board/profile используют projections/relations к одному canonical Project без semantic copies.
07Project landing имеет один hero media owner, local identity не ломает approved Global Header.
08Concept/prototype/playable/live CTA и public claims соответствуют factual source; unknown data never invented.
09G6 включает structural + visual + runtime-data + authorization tests для Projects.
