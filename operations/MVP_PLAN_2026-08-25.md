# Dementor Club — MVP Plan

Дата: 2026-08-25
Статус: current working plan
Источник: рабочий разговор команды 25.08.2026

## Цель ближайшего MVP

Пользователь должен зайти на сайт и без объяснений команды понять:

1. что такое Dementor Club;
2. что сейчас можно получить/сделать;
3. какие физические товары можно предзаказать;
4. какой онлайн-курс можно начать;
5. какие офлайн-события существуют/готовятся;
6. как пройти вступительный onboarding;
7. кто такие дементоры и что каждый из них ведёт;
8. как поддержать клуб донатом.

MVP не требует полной автоматизации всех процессов. Требуется связный пользовательский путь и сохранение данных там, где они понадобятся позже.

## P0 — продуктовая архитектура и UX

### 1. Зафиксировать сущности

Source: `operations/PRODUCT_GLOSSARY.md`.

Обязательное разделение:
- Merch = физические товары;
- Events = офлайн;
- Courses = онлайн;
- Join = onboarding/вступление;
- Donations = добровольная поддержка;
- Dementors = люди/ведущие, связанные с продуктами и событиями.

### 2. Merch preorder MVP

Состояние: контент/первая серия мерча создаётся, структура merch уже есть.

Нужно:
- рабочая страница магазина;
- несколько реальных карточек товаров;
- CTA `Предзаказ`;
- минимальная форма заказа;
- канал, куда попадает предзаказ;
- confirmation screen/email.

Не нужно на первом шаге:
- полноценная корзина;
- складская автоматизация;
- автоматическая оплата, если платёжный backend ещё не готов.

Визуалы:
- product photos/mockups;
- карточка товара;
- крупный hero магазина;
- состояния `preorder / confirmed`;
- визуальный паттерн псевдо-покупки можно использовать как сатиру, но не изображать реально состоявшееся списание денег, если его нет.

Ответственный за визуалы/товары: Nikita.

### 3. Первый Course MVP

Выбрать один курс как тестовый end-to-end продукт.

User flow:
`course landing → старт → e-mail → дневной блок 7–10 вопросов/заданий → submit → обработка → результат/следующий блок по e-mail → повтор`.

Правила:
- курс онлайн;
- многодневный/длительный;
- незавершённые вопросы остаются до ответа;
- e-mail — первая user identity;
- AI точечно на анализе входа или выхода;
- данные проектировать с возможностью позже привязать к полноценному аккаунту.

Визуалы:
- hero курса;
- карточка курса в каталоге;
- экран старта;
- дневной экран вопросов;
- экран `отправлено / ждите результат`;
- e-mail/result visual;
- progress/state pattern.

### 4. Join / onboarding MVP

Существующий `/join` сохранить как отдельную механику клуба, не превращать в курс.

User flow:
`onboarding → результат по 9 сферам → ввод e-mail → сохранить результат + e-mail → отправить результат пользователю`.

Позже: миграция данных на полноценный аккаунт/login.

Визуалы:
- текущая onboarding system;
- финальный профиль/таблица 9 сфер;
- e-mail capture screen;
- success/result screen.

### 5. Events

Добавить минимум 2 офлайн-события как полноценные сущности сайта.

Допустимо, чтобы часть будущих событий была без точной даты, но это должно быть явно показано как `planned`, а не `announced`.

Для каждого:
- название;
- статус;
- дементор/ведущий;
- концепция;
- город/место если известно;
- дата если утверждена;
- CTA;
- visual/hero + дополнительные изображения при необходимости.

Текущее подтверждённое event-содержимое в Git: Fuengirola. Второе событие требует фиксации отдельной карточкой после утверждения.

Визуалы:
- hero/poster каждого события;
- карточка в Events;
- social-ready image/OG;
- при необходимости 2–4 атмосферных изображения.

### 6. Dementors

Нужны минимум 1–2 законченных профиля для проверки структуры.

Профиль должен содержать:
- кто это;
- роль/функция;
- связанные сферы;
- программы/курсы;
- события;
- проекты;
- визуальный портрет по канону Dementor Ink.

### 7. Donations

Создать отдельную страницу/секцию `Donations`.

Функциональная цель MVP:
- объяснить, зачем клуб принимает поддержку;
- дать понятный CTA;
- подготовить место под платежную интеграцию или простую рабочую механику поддержки.

Тон: фирменный чёрный юмор. Рабочая тема — «борьба с финансовой беззаботицей». Финальный текст не считать утверждённым до отдельной редакционной фиксации.

Визуалы:
- отдельный donation hero/poster;
- сатирический псевдо-финансовый UI;
- состояния CTA/confirmation.

## P1 — техническая подготовка

### E-mail first

На текущем этапе единый идентификатор — e-mail.

Нужно предусмотреть единый data model, чтобы:
- onboarding results;
- course state;
- preorder;
- позже event registrations

можно было связать с одним e-mail и затем с будущим account ID.

### Auth readiness

Полноценную авторизацию сейчас не делать обязательным блокером MVP, но архитектура не должна мешать будущему Google login / полноценному аккаунту.

### Data/privacy

После фиксации фактических пользовательских данных и flows подготовить:
- privacy policy;
- terms/disclaimer;
- consent copy;
- правила обработки e-mail и результатов onboarding/course.

Не копировать чужой boilerplate без адаптации к реальным данным клуба.

## Definition of MVP ready

MVP можно считать продуктово собранным, когда работают/представлены end-to-end:

- [ ] merch: товар → предзаказ → заявка;
- [ ] course: старт → e-mail → дневной блок → submit → результат/следующий шаг;
- [ ] join: onboarding → e-mail → сохранённый/отправленный результат;
- [ ] events: минимум 2 карточки/страницы с корректными статусами;
- [ ] dementors: минимум 1–2 законченных профиля;
- [ ] donations: публичная страница/секция с CTA;
- [ ] mobile + smoke test;
- [ ] Site Integrity / CI не блокирует public release;
- [ ] пользовательские data flows имеют минимальные privacy/disclaimer тексты.

## Не делать сейчас

- сложную универсальную CRM;
- несколько способов доставки сообщений одновременно;
- Telegram/WhatsApp до проверки e-mail flow;
- полноценную membership billing-модель без утверждённой механики членства;
- сложный AI-agent внутри каждого шага курса;
- автоматизацию ради автоматизации до проверки пользовательского пути.
