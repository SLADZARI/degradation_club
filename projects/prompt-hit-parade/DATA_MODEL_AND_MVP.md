# ХИТ-ПАРАД ПРОМПТОВ — DATA MODEL & MVP

Status: **IDEA SUPPORT DOCUMENT / NO DEPLOY**

Цель документа — зафиксировать минимальную воспроизводимую механику проекта так, чтобы позже можно было собрать первый реальный выпуск без перепридумывания системы.

## 1. Что считаем

Базовая единица — пользовательская короткая команда, которая выполняет роль самостоятельного действия внутри уже накопленного контекста.

Примеры:

- `давай`
- `делай`
- `сделай`
- `продолжай`
- `дальше`
- `прогони`
- `посмотри`
- `исправь`
- `переделай`

Не считать автоматически как отдельный хит каждое длинное техническое задание. Длинные prompts могут существовать в архиве, но недельный чарт строится прежде всего вокруг повторяемых командных формул.

## 2. Raw record

Минимальная внутренняя запись:

```yaml
id: string
timestamp: datetime
conversation_id: private-hash
message_id: private-hash
raw_text: private
normalized_phrase: string
category: string
is_command: boolean
is_quote: boolean
is_repeated_paste: boolean
eligible_for_chart: boolean
```

`raw_text` не должен попадать в публичный output.

## 3. Aggregated prompt record

```yaml
canonical_phrase: "давай"
variants:
  - "давай"
  - "давай."
week: "2026-W35"
count: 0
distinct_days: 0
distinct_conversations: 0
rank: null
previous_rank: null
movement: "NEW"
category: "continue/execute"
verified: false
source_method: "manual|export|automated"
```

## 4. Нормализация

Первая версия должна быть консервативной.

Нормализуем:

- регистр;
- финальную пунктуацию;
- лишние пробелы;
- очевидные опечатки только если смысл однозначен.

Не объединяем автоматически разные глаголы только потому, что они похожи по функции.

Например:

`сделай` и `делай` сначала считаются раздельно.

Объединение допустимо только отдельным редакционным правилом, которое фиксируется до расчёта чарта.

## 5. Исключения

Из подсчёта исключать:

- текст ассистента;
- цитирование предыдущих сообщений;
- вставленные документы;
- системные prompts;
- автоматически повторённый UI-текст;
- копипаст одного и того же сообщения при технической ошибке;
- сообщения, содержащие чувствительные данные, если невозможно безопасно отделить командную фразу.

## 6. Рейтинг

MVP ranking:

1. `count` по canonical phrase;
2. при равенстве — больше `distinct_conversations`;
3. затем — больше `distinct_days`;
4. затем — равное место либо стабильное редакционное правило tie-break.

Нельзя менять правило после просмотра результата ради более смешного чарта.

## 7. Movement

После появления второй измеренной недели:

- `↑` — поднялся;
- `↓` — опустился;
- `—` — сохранил место;
- `NEW` — впервые в TOP;
- `RETURN` — вернулся после отсутствия.

Для первой недели все позиции имеют `NEW`, если выпуск действительно измеренный.

## 8. Возможные категории

Категория не влияет на основной рейтинг и нужна только для анализа:

- `execute` — сделай / делай;
- `continue` — продолжай / дальше;
- `inspect` — посмотри / проверь;
- `repair` — исправь / переделай;
- `run` — прогони / запусти;
- `constraint` — не меняй / оставь;
- `quality` — сделай лучше / качественнее;
- `approval` — да / давай;
- `other`.

Это рабочая классификация и не является новой клубной таксономией. Она существует только внутри проекта как техническое поле.

## 9. Метрика скрытого контекста — гипотеза

Позже можно ввести редакционную метрику `context_debt` / «сколько смысла отсутствует в буквальном prompt».

Пример:

`ДАВАЙ` — буквальный текст почти не содержит задания, но может требовать знания десятков предыдущих решений.

До появления воспроизводимого метода это **не числовая аналитическая метрика**, а редакционная характеристика.

## 10. Privacy by design

Публичная система должна хранить только:

- нормализованную фразу;
- агрегированный count;
- ranking/movement;
- безопасный редакционный комментарий.

Имена людей, названия клиентов, содержание приватных проектов и исходные сообщения не нужны для публичной ценности проекта.

Рекомендуемый принцип:

`collect privately → normalize → aggregate → redact → publish aggregate`

## 11. MVP 0 — уже сделано

- концепция сохранена;
- проект классифицирован;
- weekly format определён;
- data model определён;

Никакой публичной реализации нет.

## 12. MVP 1 — первый доказательный выпуск

Когда будет принято решение продолжать:

1. выбрать точный семидневный период;
2. получить доступный набор реальных пользовательских сообщений за этот период;
3. отделить пользовательские команды от прочего текста;
4. нормализовать фразы;
5. вручную проверить TOP 20;
6. посчитать TOP 10;
7. сохранить исходную агрегированную таблицу;
8. собрать `WEEK 01` по шаблону;
9. только после проверки решить, нужен ли сайт/social output.

## 13. MVP 2 — библиотека

После нескольких недель можно строить архив:

`/prompt-hit-parade/YYYY/WEEK-XX`

и отдельные страницы фраз:

`/prompt-hit-parade/prompt/davai`

Потенциальная страница фразы:

- текущая позиция;
- лучший rank;
- недели в чарте;
- история movement;
- variants;
- редакционная расшифровка;
- развёрнутая версия;
- связанные фразы.

URL-архитектура здесь только гипотеза для будущего сайта. Она **не является заданием на реализацию**.

## 14. MVP 3 — культурный архив

При накоплении данных проект может отвечать уже не только «что было популярно на этой неделе», но и показывать изменение человеческого языка работы с AI:

- какие prompts сокращаются;
- какие команды исчезают;
- какие новые глаголы появляются;
- насколько возрастает доля контекстно-зависимых команд;
- как меняется язык в разных типах задач.

Это потенциально превращает шутливый weekly chart в наблюдение за новой интерфейсной культурой.

## 15. Что сейчас НЕ делать

До отдельного решения не нужно:

- создавать route на официальном сайте;
- добавлять проект на Home/Projects;
- публиковать соцсети;
- придумывать fake statistics;
- обещать weekly cadence;
- строить collector без понятного источника данных;
- подключать приватные диалоги к публичному pipeline;
- объявлять проект запущенным.

Текущий результат — сохранённая, структурированная и готовая к прототипированию идея.
