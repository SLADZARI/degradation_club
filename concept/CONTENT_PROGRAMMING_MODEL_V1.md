# DEMENTOR CLUB — CONTENT & PROGRAMMING MODEL v1

Status: **WORKING CANON / content programming authority**  
Updated: **2026-09-15**

## Authority scope

Этот документ определяет, **как Dementor Club превращает отдельные Things в продолжающуюся редакционную программу, ради которой возникает смысл возвращаться**.

Он отвечает на вопросы:

- **Почему эта Thing находится в программе сейчас?**
- **Что должно идти рядом, до или после неё?**
- **Когда старая Thing снова становится актуальной?**
- **Как возникает ожидание следующей вещи без превращения Dementor в ленту, контент-фабрику или notification machine?**

Документ опирается на:

- `concept/DEMENTOR_CLUB_JTBD_PRODUCT_THESIS_V2.md`;
- `concept/CJM_CLUB_V1.md`;
- `concept/AUDIENCE_ENTRY_MAP_V1.md`;
- `concept/VALUE_ARCHITECTURE_V1.md`;
- `concept/PRODUCT_MODEL_V1.md`;
- `concept/BOARD_PRODUCT_MODEL_V1.md`.

Он не переопределяет Thing, Form, Release, Project, Production State, Participation или History.

`06 · Board Product Model` отвечает:

> **как Board показывает Thing сейчас.**

`07 · Content & Programming Model` отвечает:

> **почему именно эта Thing важна программе сейчас и какое продолжение человек начинает ожидать.**

---

# 0. Главный принцип

Dementor Club — не архив Things.

И не бесконечная лента новых публикаций.

Dementor должен ощущаться как:

> **место, где что-то происходит и где потом появляется следующая вещь.**

Каноническая формула:

**THING → PROGRAMMING MOMENT → EXPERIENCE → EXPECTATION → NEXT PROGRAMMING MOMENT**

По-человечески:

**появилось что-то стоящее → мы вынесли это в программу → человек это увидел → теперь у происходящего есть продолжение**

Главная формула программы:

**WHAT MATTERS NOW + WHAT CONTINUES + WHAT MAY HAPPEN NEXT**

При этом последнее существует только тогда, когда реальное продолжение действительно есть.

---

# 1. Editorial Program ≠ PROGRAM entity

В продукте уже существует canonical source entity `PROGRAM`, например для Course / Practice и других продуктовых сущностей.

Это не то же самое, что **Editorial Program клуба**.

Каноническое разделение:

```text
PROGRAM entity
=
конкретная продуктовая / operational сущность

EDITORIAL PROGRAM
=
редакционно собранная последовательность Things и значимых изменений во времени
```

Нельзя менять source ontology ради Programming Model.

**SOURCE TYPE ≠ FORM ≠ EDITORIAL PROGRAM.**

---

# 2. Programming ≠ Content Taxonomy

В клубе уже существует отдельный CANON для тематической классификации:

`operations/CONTENT_TAXONOMY_AND_DEMENTOR_LEVELS.md`

Он отвечает:

> **о чём эта Thing и где она находится в смысловой карте клуба?**

Через:

- 9 постоянных сфер;
- thematic tags;
- уровни дементорства там, где они действительно применимы;
- связи между тематически родственными объектами.

`07 · Content & Programming Model` отвечает на другой вопрос:

> **почему эту Thing стоит вынести в актуальную программу именно сейчас?**

Поэтому:

```text
TAXONOMY
=
semantic / thematic classification

PROGRAMMING
=
editorial relevance in time
```

`Programming reason`, Series, Cycle, editorial window и `why_now` **не создают параллельную тематическую классификацию** и не заменяют сферу / теги.

И наоборот, принадлежность Thing к сфере или тегу сама по себе не является достаточным Programming reason.

---

# 3. Thing не находится в программе постоянно

Thing может существовать годами.

Это не означает, что она должна годами занимать место в актуальной программе.

Программа выбирает:

> **почему на эту Thing стоит снова посмотреть именно сейчас?**

Таким образом:

**THING EXISTENCE ≠ PROGRAM RELEVANCE**

Thing может временно исчезнуть из активной программы, оставаясь:

- существующей;
- выпущенной;
- доступной;
- частью Project;
- частью истории Dementor.

И затем вернуться.

Уход из программы не означает:

- `STOPPED`;
- `ARCHIVED`;
- `DELETED`;
- завершение Project.

Это только редакционное решение:

> **сейчас нет достаточно сильного повода снова выносить эту Thing вперёд.**

---

# 4. Programming Moment

Каноническая единица `07`:

## PROGRAMMING MOMENT

Это **редакционное решение сделать Thing заметной сейчас по конкретной причине**.

Programming Moment **не является новой Thing и не обязан становиться отдельной DB entity / table**.

Это semantic / editorial layer над Product Model.

Формула:

```text
THING
+
MEANINGFUL DELTA OR EDITORIAL REASON
+
WHY NOW
+
EDITORIAL WINDOW
+
SEQUENCE CONTEXT
=
PROGRAMMING MOMENT
```

Одна Thing может иметь много Programming Moments.

Например:

1. Thing впервые вышла;
2. позже появился playable build;
3. через неделю понадобились тестировщики;
4. потом Thing исчезла из актуальной программы;
5. через три месяца с ней произошло что-то неожиданное.

Это всё одна Thing.

Но разные Programming Moments.

Каноническое правило:

**PROGRAMMING MOMENT IS A DECISION OVER EXISTING SEMANTICS, NOT A NEW PRODUCT OBJECT BY DEFAULT.**

---

# 5. Причины войти в программу

Рабочая модель причин:

| Programming reason | Почему Thing снова важна |
| --- | --- |
| `NEW RELEASE` | появился новый самостоятельный experience |
| `CONTINUATION` | у знакомой Thing появилось содержательное продолжение |
| `MAKING PROOF` | в процессе появилось что-то уже достойное внимания |
| `OPEN PARTICIPATION` | возникла конкретная возможность вписаться |
| `HISTORY EVENT` | с Thing реально что-то произошло |
| `RESURFACE` | старая Thing снова стала содержательно уместна |
| `SERIES EPISODE` | появилась новая часть узнаваемой линии |
| `EDITORIAL PAIRING` | две или несколько Things раскрывают друг друга |
| `TIME WINDOW` | experience доступен сейчас в реальном ограниченном окне |

Это не Product lifecycle.

И не новые статусы Thing.

Одна Thing может одновременно быть:

`MAKING + RELEASED`

и войти в программу по причине:

`OPEN PARTICIPATION`.

Programming reason объясняет **редакционное WHY NOW**.

Board `projection_reason` затем может использовать эту информацию для выбора presentation.

Но Programming Model не переопределяет Board Model.

---

# 6. Meaningful delta

Сам факт изменения записи не является поводом для программы.

Не являются автоматически meaningful delta:

- изменение `updated_at`;
- редактирование текста;
- новая реакция;
- комментарий;
- переименование;
- технический deploy;
- перемещение карточки;
- повторная публикация той же ссылки.

Канонический вопрос:

> **Изменилось ли что-то для человека, которому эта Thing уже была интересна?**

Если нет:

**NO PROGRAMMING MOMENT.**

Это один из главных способов не превратить Dementor в имитацию активности.

---

# 7. Свежесть

Свежесть — редакционное свойство, а не дата.

Поэтому сохраняется правило:

**FRESHNESS ≠ CREATED_AT ≠ PUBLISHED_AT**

Старая Thing может быть самой свежей вещью программы, если:

- с ней произошло что-то новое;
- появился новый Release;
- она неожиданно продолжилась;
- открылось участие;
- другая Thing создала для неё новый контекст.

И наоборот:

Thing, опубликованная пятнадцать минут назад, может не иметь программной ценности.

---

# 8. Ритм программы

Ритм — не количество публикаций в день.

Ритм — это ощущение:

> **«здесь снова что-то произошло».**

Канонический принцип:

**PREDICTABLE CONTINUATION WITHOUT PREDICTABLE SAMENESS**

Аудитория постепенно понимает:

> Dementor продолжится.

Но не знает заранее, будет ли следующей вещью:

- текст;
- игра;
- видео;
- событие;
- эксперимент;
- инструмент;
- физический объект;
- продолжение старой Thing.

В этом состоит часть характера клуба.

Формы могут меняться.

Продолжается сам способ смотреть.

---

# 9. Несколько скоростей

Программа может одновременно жить на разных временных масштабах.

## Быстрый слой

Небольшая законченная Thing, точное наблюдение, изображение, короткое видео или другой самостоятельный experience.

## Средний слой

Series, experiment, Event, следующая версия уже знакомой Thing.

## Длинный слой

Game, Course, Physical Product, большой Project или другая Thing, которая требует продолжительного производства.

Это не квоты.

Не требуется постоянно иметь все три слоя.

Смысл модели — позволить программе жить между большими Releases, **не заполняя паузу пустым контентом**.

---

# 10. Release не обязан немедленно требовать следующего поста

Одна сильная Thing может оставаться главным событием программы столько, сколько она действительно выдерживает внимание.

Не требуется после Release автоматически производить:

- «как мы это делали»;
- «5 фактов о проекте»;
- «что дальше»;
- «закулисье»;
- «мы всё ещё здесь».

Продолжение появляется только тогда, когда появилось содержание для продолжения.

Канонический принцип:

**NO DELTA → NO UPDATE**

---

# 11. Series

Series — редакционная связь между несколькими Things, создающая узнаваемое продолжение.

Series не является Project.

Series не является Product Form.

Series не обязана иметь отдельную продуктовую страницу.

Ключевой признак Series:

> **после одной части человек понимает, какого типа продолжение здесь в принципе может появиться.**

При этом продолжение не должно быть механическим повторением шаблона.

Хорошая Series создаёт:

- узнавание;
- ожидание;
- вариативность;
- возможность вернуться к уже знакомой линии.

Series может закончиться.

Ей не нужен бессрочный commitment.

---

# 12. Recurring Format

Recurring Format отличается от Series.

**Series обещает продолжение линии.**

**Recurring Format даёт редакции повторяемый способ делать разные Things.**

Например, один и тот же способ наблюдения или подачи может использоваться для совершенно разных тем.

Product Form при этом может меняться.

Поэтому:

**EDITORIAL FORMAT ≠ PRODUCT FORM**

Recurring Format полезен, если он:

- ускоряет узнавание;
- усиливает Dementor POV;
- позволяет сравнивать разные наблюдения;
- не превращается в обязательный шаблон.

Когда формат начинает производить материал только потому, что существует рубрика, формат нужно остановить.

---

# 13. Cycle / Season

Редакционный Cycle или Season допустим, если он помогает собрать несколько самостоятельных Things в понятный временный контекст.

Но Season не является обязательной структурой Dementor.

Season может появиться вокруг:

- реального события;
- эксперимента;
- темы;
- поездки;
- Project;
- временного исследования;
- Series связанных наблюдений.

Канонический принцип:

> **Сначала существуют сильные Things и реальная связь между ними. Потом, если полезно, появляется Cycle.**

Не наоборот.

Нельзя придумывать Things для заполнения заранее нарисованного сезона.

Окончание Cycle не меняет lifecycle входящих в него Things.

---

# 14. Authored program

Dementor остаётся редакционной программой, даже когда в неё начинают приносить материал другие люди.

Contribution не становится частью программы автоматически.

Правильная цепочка:

**CONTRIBUTION → EDITORIAL REACTION → возможно THING → возможно PROGRAMMING MOMENT**

Не:

**USER POSTED → FEED UPDATED**

Программа остаётся отобранной.

Редакция может:

- подхватить Observation;
- соединить несколько contributions;
- пригласить автора;
- изменить Form;
- создать новую Thing;
- добавить contribution к уже существующей Thing;
- осознанно ничего не выпускать.

Количество входящих contributions не определяет объём публичной программы.

---

# 15. Project activity ≠ Program

Project может быть очень активным внутри.

Но аудитории не нужно видеть каждое действие Project.

В программу попадают только моменты, которые сами выдерживают внимание.

Поэтому:

```text
PROJECT ACTIVITY
→ editorial selection
→ PROGRAMMING MOMENT
```

Не:

```text
PROJECT ACTIVITY
→ automatic Board / Activity publication
```

Project существует для появления Things.

Программа существует для аудитории.

---

# 16. Selection Gate

Перед тем как вынести Thing в программу, редакция отвечает на один набор вопросов:

1. **Есть ли здесь самостоятельная ценность внимания?**
2. **Что именно изменилось?**
3. **Почему это важно сейчас?**
4. **Нужно ли человеку уже знать предыдущий контекст?**
5. **Какой experience является главным?**
6. **Создаём ли мы ожидание следующего шага?**
7. **Сможем ли мы это ожидание закрыть?**
8. **Не показываем ли мы внутреннюю активность вместо вещи?**
9. **Не пытаемся ли мы заполнить паузу?**

Если единственный аргумент:

> «давно ничего не публиковали»,

это недостаточный Programming reason.

---

# 17. Sequencing

Программа не обязана идти строго по времени.

Последовательность является редакционным решением.

Новая Thing не всегда должна стоять выше более старой.

Сильный Release может предшествовать объяснению его Project.

History знакомой Thing может быть интереснее новой небольшой публикации.

Две Things могут идти рядом, потому что между ними возникает неожиданная связь.

Канонический принцип:

**SEQUENCE BY ATTENTION, NOT DATABASE CHRONOLOGY**

При этом последовательность не должна скрывать факты или изображать старую Thing новой.

---

# 18. Не дать одному Project съесть программу

Сильный Project может производить много событий.

Это не означает, что программа Dementor должна превращаться в дневник этого Project.

Редакция должна сохранять ощущение:

> **у клуба есть программа, а не один бесконечный production log.**

Project получает место тогда, когда произвёл:

- новую Thing;
- новый Release;
- содержательный proof;
- реальную возможность Participation;
- значимый History event.

Остальная работа может оставаться за кулисами.

---

# 19. Anticipation

Программа становится сильнее, когда человек иногда знает:

> **у этого будет продолжение.**

Но anticipation допустим только при реальном open loop.

Хорошее ожидание привязано к конкретному объекту:

- следующая версия;
- следующий episode;
- результат experiment;
- Event;
- Release;
- проверка идеи;
- открытая Participation Opportunity.

Плохое ожидание:

**СКОРО**

**НЕ ПРОПУСТИТЕ**

**БОЛЬШЕ УЖЕ СОВСЕМ СКОРО**

без существующего следующего шага.

Канонический принцип:

**PROMISE ONLY WHAT ACTUALLY EXISTS AS A NEXT MOVE**

Если обещанное продолжение отменилось, это тоже можно закрыть редакционно.

Молчаливое исчезновение open loop разрушает anticipation сильнее, чем честное:

> не получилось, остановили.

---

# 20. Resurfacing

Resurfacing — возвращение уже существующей Thing в актуальную программу.

Это не новая публикация и не новый Release само по себе.

Хорошие причины:

- появился meaningful History event;
- появилась новая версия;
- открылось участие;
- возникла следующая Thing в Series;
- Thing неожиданно связалась с новой Thing;
- изменился реальный внешний контекст, благодаря которому старая Thing снова что-то показывает.

Плохая причина:

> Thing давно не показывали.

Канонический принцип:

**RESURFACE BECAUSE MEANING CHANGED, NOT BECAUSE THE FEED NEEDS FILLING**

---

# 21. Editorial retirement

Thing может временно выйти из активной программы.

Это называется здесь **editorial retirement**, а не Product State.

Thing не удаляется.

Не архивируется автоматически.

Не становится `STOPPED`.

Она просто перестаёт конкурировать за внимание сейчас.

Это позволяет программе быть конечной и читаемой.

Архив Dementor может быть большим.

Актуальная программа должна оставаться маленькой достаточно, чтобы в ней чувствовался выбор.

---

# 22. Одна программа — разные поверхности

Programming decision является общим.

Поверхности показывают его по-разному.

| Surface | Роль |
| --- | --- |
| Home | короткий редакционный cut: что сейчас стоит внимания |
| Board | жизнь Things сейчас: Release / Making / Participation / History |
| Activity | meaningful deltas во времени |
| Thing Detail | полный контекст конкретной Thing |
| Project | продолжительность и связь нескольких Things |
| Dementor Profile | авторская линия через сделанные Things |
| External distribution | отдельный вход в конкретный Programming Moment |

Home не должен копировать Board.

Activity не должен становиться вторым Board.

External distribution не должна публиковать каждое внутреннее изменение.

Но все поверхности должны исходить из одной редакционной правды:

> **почему эта Thing важна сейчас.**

---

# 23. Programming layer

Implementation может хранить Programming decisions любым способом.

Этот документ не требует отдельной таблицы.

Семантически достаточно уметь выразить:

```text
subject / Thing

programming_reason

why_now

priority / editorial weight

active window

series / cycle context, if any

previous / next relation, if meaningful

anticipated_next, if real

surface eligibility

editorial owner
```

Это не новая Product ontology.

Это редакционная проекция над существующей Product Model.

Канонический поток:

```text
THING / RELEASE / HISTORY / PARTICIPATION / PROJECT SIGNAL
→ EDITORIAL PROGRAMMING DECISION
→ SURFACE-SPECIFIC PROJECTION
```

---

# 24. Как программа живёт без постоянного net-new content

Dementor не обязан всё время производить новые сущности.

Программа может оставаться живой за счёт реальных изменений уже существующих Things.

Одна Thing во времени может естественно дать:

- первый Release;
- новую версию;
- Participation Opportunity;
- History event;
- продолжение Series;
- новую связанную Thing.

Но это не означает, что одну Thing нужно искусственно разрезать на шесть публикаций.

Каноническое правило:

> **Один реальный факт может создать новый Programming Moment. Один Programming Moment не должен притворяться шестью фактами.**

---

# 25. Главный ритм Dementor

На уровне аудитории программа должна постепенно создавать ощущение:

**что-то вышло**

потом:

**с этим что-то произошло**

потом:

**рядом появилась другая странная вещь**

потом:

**к чему-то можно приблизиться**

потом:

**что-то, что раньше мутили, наконец существует**

И не обязательно именно в таком порядке.

Задача не научить человека структуре продукта.

Задача — чтобы он начал чувствовать:

> **«Хочу посмотреть, что у них там следующим случится».**

---

# 26. Anti-patterns

Критический anti-pattern:

**PROGRAM = CHRONOLOGICAL FEED**

Также запрещённые направления:

- публиковать ради установленной частоты;
- автоматически выводить каждое действие Project;
- автоматически публиковать contributions;
- считать комментарий или reaction новым событием программы;
- создавать Series после одной Thing только ради упаковки;
- придумывать Cycle и затем заполнять его материалом;
- постоянно показывать `MAKING`, если ничего содержательно не меняется;
- использовать `coming soon` без существующего продолжения;
- считать cross-post новой Thing;
- переиздавать старый материал как новый без указания причины возвращения;
- делать аккаунтные notifications основой retention;
- позволять одному Project вытеснить всю остальную программу.

Главный anti-signal:

> **Dementor выглядит занятым, но человеку нечего нового увидеть, пережить или ожидать.**

---

# 27. Editorial QA

Перед включением Programming Moment редакция должна суметь закончить фразу:

> **«Мы показываем эту Thing сейчас, потому что…»**

Ответ должен содержать реальную причину.

Не:

> потому что она новая в CMS.

Не:

> потому что давно ничего не было.

Не:

> потому что алгоритму нужна активность.

А, например:

> появилась версия, в которую уже можно играть.

> впервые можно вписаться.

> эксперимент закончился неожиданным образом.

> появилась следующая часть.

> старая Thing вдруг получила реальное продолжение.

Если фразу закончить нечем:

**Thing сейчас не нужна в программе.**

---

# 28. Boundary with 08 · Return Loops

`07 · Content & Programming Model` является supply-side моделью.

Он определяет:

> **какие повторяющиеся редакционные причины возвращения создаёт клуб.**

`08 · Return Loops` должен определить audience-side:

> **почему конкретный человек вспоминает о Dementor, возвращается и какой trigger / expectation / continuity запускает этот возврат.**

То есть:

```text
07
PROGRAM CREATES REASONS TO RETURN

08
PERSON EXPERIENCES A REASON AND RETURNS
```

Не смешивать эти два слоя.

# Canonical summary

Dementor Club не требует бесконечного производства контента.

Ему требуется **живая редакционная программа**.

Программа появляется, когда редакция умеет выбирать:

- **что важно сейчас;**
- **что действительно продолжилось;**
- **что стоит вернуть;**
- **за чем имеет смысл следить;**
- **где существует реальное следующее действие.**

Главная формула:

**THING + WHY NOW + SEQUENCE + REAL CONTINUATION = PROGRAM**

Главный критерий:

> **человек начинает ждать не следующий пост, а следующую вещь Dementor.**
