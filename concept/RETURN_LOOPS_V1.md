Return Loop описывается как:

**TRIGGER → EXPECTATION → RETURN → PAYOFF → MEMORY / NEXT EXPECTATION**

Главная проверка:

> **Человек возвращается потому, что ожидает следующую ценность, а не потому, что продукт создал ему долг по уведомлениям.**

---

# 0. Главный принцип

Dementor не должен удерживать человека искусственным engagement loop.

Не требуется, чтобы человек:

- возвращался каждый день;
- поддерживал streak;
- закрывал unread;
- отвечал другим пользователям;
- боялся пропустить активность;
- проверял notifications;
- поддерживал социальный статус.

Канонически:

**RETURN FOLLOWS VALUE, NOT DEBT**

И:

**PROGRAM MEMORY > NOTIFICATION DEBT**

Хороший Return Loop работает даже тогда, когда человек сам вспоминает о Dementor без push.

---

# 1. Что такое Return Loop

Return Loop — это повторяемая причинная цепочка, в которой уже пережитая ценность создаёт конкретное ожидание будущей ценности.

Минимальная структура:

```text
TRIGGER
↓
EXPECTATION
↓
RETURN
↓
PAYOFF
↓
NEXT EXPECTATION or SATISFIED EXIT
```

Не каждый Return обязан порождать следующий Return.

Полностью нормальный исход:

> вернулся → получил опыт → снова ушёл.

Consumption remains success.

---

# 2. Trigger ≠ Notification

Trigger — причина вспомнить о Dementor или конкретной Thing.

Notification — только один из возможных delivery mechanisms.

Triggers могут быть:

- внутренними — человек сам вспомнил;
- программными — появилась новая Thing / Release / History;
- контекстными — в жизни встретилась похожая ситуация;
- внешними — кто-то переслал Thing;
- авторскими — появился новый материал знакомого Dementor;
- проектными — знакомая Thing получила продолжение;
- участническими — изменилось то, куда человек вписался;
- contributor-specific — редакция отреагировала на принесённое;
- utility-specific — снова возникла ситуация, где полезен конкретный метод / инструмент / Dementor.

Каноническое правило:

**DELIVERY CHANNEL ≠ RETURN REASON**

Push, Telegram, email, social и Activity могут доставить trigger, но не являются ценностью сами по себе.

---

# 3. Expectation

Return начинается до клика.

Человек возвращается, потому что предполагает:

> **«там появилось что-то, что стоит моего внимания».**

Expectation должно быть достаточно конкретным, чтобы payoff мог его подтвердить или честно закрыть.

Хорошие expectations:

- «интересно, что они заметили дальше»;
- «хочу увидеть следующую часть»;
- «что стало с той игрой?»;
- «вышла ли уже версия, которую можно попробовать?»;
- «что редакция сказала про то, что я принёс?»;
- «что произошло там, куда я вписался?»;
- «у этого Dementor появилось что-то новое?»;

Плохие expectations:

- «у меня там, наверное, непрочитанное»;
- «надо проверить, не ответил ли кто-нибудь» как основной reason продукта;
- «надо сохранить streak»;
- «вдруг я что-то пропустил» без реальной программной причины.

---

# 4. Payoff

Return считается хорошим не потому, что человек открыл продукт.

Хороший Return должен получить payoff.

Payoff — подтверждение причины, ради которой человек вернулся.

Это может быть:

- сильная новая Thing;
- новый Release знакомой Thing;
- meaningful History;
- следующая часть Series;
- ясный progress знакомого Project;
- конкретная Participation Opportunity;
- редакционная реакция;
- новый authored work;
- полезная Intervention;
- честное закрытие ранее открытого ожидания.

Канонический вопрос:

> **Вернувшись, получил ли человек то изменение, которое имело смысл проверять?**

Если продукт регулярно вызывает Return без payoff, возникает notification debt и доверие к следующему trigger падает.

---

# 5. Editorial Return Loop

## Trigger

Появилась новая сильная Thing в программе.

## Expectation

> **«Что они заметили на этот раз?»**

## Return

Человек открывает Home / Board / прямую Thing / внешний distribution entry.

## Payoff

Новая самостоятельная вещь оправдывает внимание.

## Next expectation

> **«Интересно, что будет следующим».**

Это главный базовый loop Program Audience.

Он не требует follow, регистрации или участия.

---

# 6. Anticipation Return Loop

## Trigger

Ранее программа показала реальный open loop:

- upcoming Release;
- следующую часть;
- результат эксперимента;
- продолжение Project;
- конкретное событие;
- Thing в стадии Making с понятным следующим шагом.

## Expectation

> **«Хочу дождаться, что из этого получится».**

## Return

Человек возвращается проверить продолжение.

## Payoff

Open loop либо:

- закрыт новым Release / History / результатом;
- честно обновлён;
- честно закрыт как STOPPED / отменённый / не получившийся.

Не-payoff:

вечное `СКОРО`.

Каноническое правило:

**OPEN LOOP MUST EVENTUALLY CLOSE OR CHANGE TRUTHFULLY**

---

# 7. Serial Return Loop

## Trigger

Thing является частью Series или имеет явное смысловое продолжение.

## Expectation

> **«Что будет в следующей части?»**

## Return

Человек возвращается к линии, а не обязательно ко всему клубу.

## Payoff

Следующая часть:

- узнаваема как продолжение;
- добавляет новый взгляд;
- не является механическим повтором.

## Failure mode

Series продолжает существовать после того, как закончились наблюдения, только потому что «рубрика должна выходить».

---

# 8. Thing Continuity Loop

## Trigger

Человек уже пережил конкретную Thing и запомнил её.

## Expectation

> **«Что стало именно с этой штукой?»**

## Return

Новый Release, History event, remix, event, новая Form или другое реальное продолжение возвращают человека к знакомой Thing.

## Payoff

Человек получает continuity без необходимости следить за всем клубом.

Этот loop особенно важен для старых Things: программа может вернуть их без fake freshness.

---

# 9. Dementor Return Loop

## Trigger

Человеку понравился взгляд / практика конкретного Dementor.

## Expectation

> **«Что он сделал ещё?»**

## Return

Через новую Thing, authored line, Project или contextual work.

## Payoff

Новая работа продолжает авторскую практику.

Не payoff:

social feed человека ради самого человека.

Канонический принцип:

**FOLLOW THE WORK, NOT THE PROFILE ACTIVITY**

Dementor Return Loop не должен превращаться в creator-influencer loop.

---

# 10. Project Return Loop

## Trigger

Человек видел Thing / prototype / открытый Project на стадии Making.

## Expectation

> **«Во что это превратилось?»**

## Return

Через meaningful Project delta.

## Payoff

Должно появиться что-то, что само выдерживает внимание:

- proof;
- prototype;
- Release;
- Participation Opportunity;
- значимый History event.

Не payoff:

- новая задача;
- внутренний созвон;
- переписанный roadmap;
- «работа продолжается» без нового experience.

Каноническое правило:

**PROJECT ACTIVITY DOES NOT EARN RETURN BY ITSELF**

---

# 11. History Return Loop

## Trigger

С уже выпущенной Thing произошло что-то значимое.

## Expectation

> **«Что с ней случилось после выпуска?»**

## Return

History resurfacing.

## Payoff

Реальное последствие:

- люди сыграли;
- никто не сыграл, и это стало фактом истории;
- появилась новая версия;
- Thing показали где-то ещё;
- возник remix;
- Thing породила другую Thing;
- вернулись спустя время;
- событие состоялось;
- эксперимент дал результат.

History Loop позволяет программе жить не только за счёт net-new Things.

---

# 12. External Trigger Loop

## Trigger

Человек получает Dementor извне:

- share;
- Telegram;
- social;
- search;
- событие;
- рекомендация;
- физический объект;
- другая площадка.

## Expectation

Сначала может отсутствовать ожидание клуба вообще.

После повторных encounters возникает память:

> **«А, это снова они. Посмотрим».**

## Return

Человек возвращается через конкретную Thing.

## Payoff

Thing снова оправдывает внимание и укрепляет Program Memory.

Успех этого loop — не просто referral traffic, а постепенный переход:

**external encounter → remembered source → intentional return**

---

# 13. Contributor Return Loop

## Trigger

Человек что-то принёс.

## Expectation

> **«На это действительно посмотрят?»**

## Return

Человек возвращается не ради generic notification, а ради editorial outcome.

## Payoff

Осмысленная редакционная реакция:

- observation подтверждён;
- предложен другой угол;
- найден merge с другой Thing;
- выбрана другая Form;
- приглашение делать вместе;
- осознанно решено ничего не выпускать.

Канонический principle:

**EDITORIAL RESPONSE > SUBMISSION STATUS**

`received / viewed / processed` сами по себе не являются payoff.

---

# 14. Participation Return Loop

## Trigger

Человек вписался в конкретную Thing / Project.

## Expectation

> **«Что произошло после моего действия и нужен ли я дальше?»**

## Return

Через continuation конкретного участия.

## Payoff

Человек понимает:

- действие принято;
- что изменилось;
- есть ли следующий шаг;
- где продолжение;
- закончилась ли его часть.

Канонический принцип:

**NO REACTION VACUUM**

Но это не означает бесконечную social conversation.

Участие может нормально закончиться после одного meaningful action.

---

# 15. Utility Return Loop

## Trigger

В жизни снова возникает конкретная ситуация, которую человек уже связывает с Dementor practice / method / tool / course / intervention.

## Expectation

> **«У них было что-то именно про это».**

## Return

К конкретной Thing, Intervention, Dementor practice или contextual product.

## Payoff

Реальная utility:

- инструмент;
- метод;
- курс;
- событие;
- intervention;
- другой applicable experience.

Utility Loop может быть редким, но сильным.

Он не требует превращать весь Dementor в каталог услуг.

Канонически:

**SITUATION → MEMORY → RETURN → CONTEXTUAL VALUE**

---

# 16. Search / Memory Return

Не все Returns начинаются из платформенного trigger.

Сильный продукт формирует memory cue.

Человек может спустя недели вспомнить:

- название Thing;
- образ;
- формулировку;
- Dementor;
- Project;
- конкретный взгляд;
- ситуацию.

И самостоятельно найти путь назад.

Это один из самых здоровых признаков Program Value.

Канонический принцип:

**BE MEMORABLE ENOUGH TO BE FOUND AGAIN**

---

# 17. Passive Return vs Active Follow

Return Loop существует **до и независимо от механики Follow**.

Человеку не нужно нажимать `следить`, `подписаться` или создавать специальную relation, чтобы существовало ожидание:

- что станет с конкретной Thing;
- что выпустит конкретный Dementor;
- во что превратится Project;
- чем закончится Series;
- появится ли следующая версия.

Это **Passive Return**: continuity живёт в памяти человека, программе и реальном развитии объекта.

Пример:

> человек сыграл в prototype, ничего не подписал, через месяц увидел продолжение или сам вспомнил о нём и вернулся.

Это полноценный Thing / Project Return Loop.

## Active Follow

Follow — явный способ сказать системе:

> **«это ожидание для меня уже существует; помоги мне не потерять его».**

Active Follow может улучшать:

- routing relevant Activity;
- notification eligibility;
- prioritization continuation;
- персональную видимость meaningful History / Release.

Но Follow **не создаёт ценность и не создаёт continuity сам по себе**.

Если у объекта нет meaningful continuation, follow relation не даёт продукту права генерировать активность ради активности.

Канонические правила:

**CONTINUITY ≠ SUBSCRIPTION RELATION**

**FOLLOW EXPLICITLY RECORDS EXPECTATION; IT DOES NOT CREATE THE EXPECTATION.**

И:

**NO FOLLOW REQUIRED FOR A HEALTHY RETURN LOOP.**

Из этого следует важное продуктовое ограничение: нельзя измерять здоровье Thing / Dementor / Project loops только количеством follows или conversion в подписку.

Человек может быть сильным returning audience, никогда не используя Follow.

---

# 18. Return surfaces

Return reason не принадлежит поверхности.

Одна и та же причина может привести на разные surfaces.

| Return intent | Вероятная поверхность |
|---|---|
| посмотреть что нового | Home / Board |
| продолжить знакомую Thing | Thing Detail / direct Release |
| увидеть продолжение автора | Dementor projection / authored Thing |
| проверить Project | Project / Thing produced within Project |
| увидеть outcome contribution | contribution / editorial response context |
| продолжить participation | конкретная Thing / Project |
| использовать utility | direct contextual Thing / Intervention |

Канонический principle:

**ROUTE TO THE EXPECTED VALUE, NOT TO A GENERIC DASHBOARD**

Не отправлять человека сначала в Activity / account home только потому, что технически trigger связан с аккаунтом.

---

# 19. Activity и notifications

Activity может помочь доставить meaningful return trigger.

Но Activity не должен становиться самостоятельным engagement engine.

Хорошая Activity запись отвечает:

> **что значимого изменилось у вещи, которую мне есть смысл помнить?**

Плохая:

- кто-то лайкнул;
- кто-то открыл;
- поле обновилось;
- карточку передвинули;
- Project был активен;
- «у вас 7 новых событий».

Notification допустим, если он несёт конкретный payoff promise.

Например:

> версия, которую ты тестировал, вышла.

лучше, чем:

> у вас новое уведомление.

Канонический принцип:

**NOTIFY THE CHANGE, NOT THE EXISTENCE OF A NOTIFICATION**

---

# 20. Frequency

Нет канонической цели максимизировать Return Frequency.

Разные loops естественно имеют разную скорость:

- Editorial — может быть часто;
- Series — по собственной частоте;
- Project — только по meaningful delta;
- History — иногда через месяцы;
- Utility — по жизненной ситуации;
- Contributor / Participation — пока существует конкретный open loop.

Поэтому:

**HEALTHY RETURN ≠ DAILY RETURN**

Человек, который возвращается раз в месяц на каждую сильную Thing, может быть более здоровой аудиторией, чем человек, ежедневно закрывающий notifications.

---

# 21. Return closure

Хороший loop умеет завершаться.

Не каждое ожидание нужно сохранять навсегда.

Loop закрывается, если:

- Series закончилась;
- Project остановлен;
- Participation завершена;
- contribution получил editorial outcome;
- event состоялся;
- эксперимент завершён;
- новая версия вышла и следующая пока не обещана.

Канонический principle:

**CLOSE LOOPS INSTEAD OF MANUFACTURING PERMANENT PENDING STATES**

После payoff человек может уйти без нового CTA.

---

# 22. Loop stacking

Один Return может активировать несколько loops.

Например:

человек вернулся ради Dementor Battle как Project Loop,

увидел новый Release,

сыграл,

заметил Participation Opportunity,

а потом начал ждать следующую версию.

Это нормально.

Но surface не должен показывать человеку все возможные loops одновременно.

Канонически:

**ONE PRIMARY RETURN PROMISE PER MOMENT**

Остальные continuation paths могут быть доступны вторично.

---

# 23. Return priority

Когда одновременно существует несколько причин вернуть человека, приоритет определяется не технической свежестью, а силой ожидаемой ценности.

Рабочая логика:

1. promised continuation / open loop closure;
2. directly relevant new Release / meaningful History;
3. participation / contributor outcome;
4. authored / series continuation;
5. broad editorial discovery;
6. generic platform activity.

Последний пункт обычно вообще не должен быть standalone trigger.

---

# 24. Metrics

Return Loops не требуют одной универсальной метрики.

Нужны как минимум:

## Audience Return

Вернулся ли человек за новой программой?

## Expected-value Return

Вернулся ли человек после конкретного previously opened expectation?

## Payoff Rate

Какой процент meaningful return triggers действительно приводит к ожидаемой ценности?

## Thing Continuity Return

Возвращаются ли к знакомым Things после Release / History / continuation?

## Contributor Return

Возвращаются ли после editorial outcome?

## Participation Continuation

Возвращаются ли после первого meaningful action, когда continuation действительно нужен?

## Direct / Memory Return

Возвращаются ли без platform notification через direct / search / remembered Thing?

## Return Quality

Есть ли после Return реальное consumption / use / continuation, а не только open app / open Activity?

---

# 25. Anti-signals

Главные anti-signals:

- растёт open rate notifications, но не consumption Things;
- Return всё чаще начинается с unread debt;
- Activity открывают чаще программы;
- пользователь возвращается проверить responses, но новых Things почти нет;
- Project генерирует много уведомлений без meaningful delta;
- anticipation loops не закрываются;
- старые Things resurfaced без новой причины;
- generic email / push frequency увеличивается для компенсации слабой программы;
- daily active растёт, а Thing → Thing и Audience Return на Releases не растут;
- социальное взаимодействие самовоспроизводится без Things.

Критический anti-signal:

> **человек регулярно возвращается, но всё реже может ответить, зачем именно стоило вернуться.**

---

# 26. Product QA for any Return trigger

Перед созданием механики возврата ответить:

1. Какой именно loop это обслуживает?
2. Что является trigger?
3. Какое конкретное expectation мы создаём?
4. Куда человек должен вернуться?
5. Какой payoff его там ждёт?
6. Это реальная ценность или account activity?
7. Нужно ли вообще отправлять notification?
8. Можно ли дать человеку найти это самому через Program / Memory?
9. Когда этот loop должен закрыться?
10. Что произойдёт с доверием, если человек вернётся и payoff не будет?

Если нельзя назвать payoff:

**НЕ СОЗДАВАТЬ RETURN MECHANIC.**

# 27. Relationship with Content & Programming Model

`07` создаёт supply:

```text
THING / RELEASE / HISTORY / PARTICIPATION / PROJECT SIGNAL
→ EDITORIAL PROGRAMMING DECISION
→ PROGRAMMING MOMENT
```

`08` описывает audience response:

```text
PROGRAMMING MOMENT / CONTEXTUAL TRIGGER
→ EXPECTATION
→ RETURN
→ PAYOFF
→ MEMORY / NEXT EXPECTATION
```

Связка документов:

**PROGRAMMING MOMENT CREATES A POSSIBLE REASON TO RETURN.**

**RETURN LOOP EXISTS ONLY WHEN A PERSON CAN FORM AN EXPECTATION AND RECEIVE A PAYOFF.**

Не каждый Programming Moment требует персонального notification.

Не каждый Return требует нового Programming Moment: Utility / Memory / External triggers могут вернуть человека к уже существующей Thing.

# 28. Boundary with 09 · Contribution Model

`08` определяет Contributor Return только как loop:

**принёс → ожидает editorial reaction → вернулся → получил editorial outcome.**

`09 · Contribution Model` должен определить саму систему contribution:

- что считается Contribution;
- как оно появляется;
- какие submission / editorial states существуют;
- как редакция работает с Observation;
- merge / reframe / no-action;
- когда Contribution становится Thing;
- когда возникает Project;
- credit / authorship;
- rejection / closure.

То есть:

**08 owns why contributor returns.**

**09 owns what actually happens to contribution.**

# Canonical summary

Dementor не должен строить retention из привычки проверять продукт.

Он должен создавать память о ценности и реальные причины вернуться.

Главная формула:

**TRIGGER → EXPECTATION → RETURN → PAYOFF → MEMORY / NEXT EXPECTATION**

Базовый loop:

**новая Thing → «что они заметили?» → вернулся → получил опыт → помнит Dementor как источник следующей Thing**

Но Return может также происходить вокруг:

- anticipation;
- Series;
- конкретной Thing;
- Dementor;
- Project;
- History;
- external encounter;
- Contribution;
- Participation;
- contextual Utility.

Главный guardrail:

> **RETURN FOLLOWS VALUE, NOT DEBT.**

И главный критерий здоровья:

> **после возвращения человек понимает, зачем ему стоило вернуться.**
