# DEMENTOR CLUB — COMMERCIAL OFFER & PRICING EXPERIMENTS v1

Status: **DRAFT / COMMERCIAL VALIDATION PLAN**  
Updated: **2026-09-15**

## Purpose

Turn monetization architecture into a small set of testable commercial hypotheses.

Payment attaches to a concrete value object, not status.

---

# 1. What is not approved

Not approved as current business facts:

- universal paid Membership;
- subscription as default model;
- premium status ladder;
- broad paid catalog;
- dynamic pricing engine;
- aggressive discounting;
- checkout before fulfillment readiness.

---

# 2. First offer classes to validate

## O1 — Paid digital Thing / Tool

### Candidate price hypothesis

`€8–15` or local equivalent.

### Value object

One complete digital Thing / Tool / edition.

### Success evidence

- payment;
- actual use;
- low refund/failure;
- another Thing opened later;
- repeat purchase or explicit interest.

### Failure mode

People like the idea but do not pay at literal price.

---

## O2 — Live online experience / Practice

### Candidate price hypothesis

`€25–50` per participant.

### Value object

One concrete facilitated session with a clear premise and duration.

### Success evidence

- paid attendance;
- show-up;
- completed experience;
- participant asks for another occurrence / related Thing.

### Failure mode

Demand exists only while free or requires founder-specific persuasion.

---

## O3 — Small offline experience / Event

### Candidate price hypothesis

`€90–190` depending on duration / location / cost base.

### Value object

One bounded Event experience.

### Success evidence

- fill rate at real price;
- no misleading scarcity;
- attendance;
- fulfillment quality;
- repeat/referral.

### Failure mode

Venue / travel / team cost destroys contribution margin.

---

## O4 — High-touch Intervention

### Candidate price hypothesis

Start only after one narrow Situation is validated.

Price must follow scope / payer / duration, not “access to Dementor”.

### Success evidence

- qualified Situation;
- payment;
- completed intervention;
- observable outcome / useful consequence;
- referral / repeat.

---

## O5 — Physical Thing

### Price logic

Cost-plus is not enough by itself, but unit economics must include:

- manufacturing;
- packaging;
- payment fees;
- shipping/handling;
- returns/replacements;
- unsold inventory risk.

Preorder may be tested only when payment and fulfillment readiness are real.

---

# 3. Pricing method

For early tests use:

- one clear offer;
- 2–3 price cells maximum;
- same underlying value;
- no status tiers.

Possible methods:

- sequential cohort pricing;
- limited A/B where sample is sufficient;
- reservation/deposit before full production where lawful and fulfillable.

Do not interpret willingness-to-pay interviews as payment evidence.

---

# 4. Offer contract

Every paid test must define before launch:

```text
VALUE OBJECT
PAYER
USER
PRICE
CURRENCY
WHAT IS INCLUDED
WHAT IS NOT INCLUDED
DELIVERY DATE / WINDOW
CAPACITY
PAYMENT METHOD
CANCELLATION / REFUND RULE
FAILURE HANDLING
SUPPORT OWNER
DATA / LEGAL REQUIREMENTS
SUCCESS SIGNAL
STOP CONDITION
```

If these cannot be stated literally, the offer is not ready.

---

# 5. First recurring experiment gate

Do not define recurring pricing until:

- at least one paid object is used successfully;
- repeat purchase appears across independent people;
- a recurring need can be named;
- recurring fulfillment cadence is operationally sustainable.

Then test one recurring package, not three status tiers.

Working research corridor may be used for planning only, not current public pricing.

---

# 6. Discount rules

Discounts must not hide weak willingness to pay.

Allowed reasons:

- early pilot in exchange for explicit research participation;
- annual prepayment only after recurring value exists;
- partner subsidy clearly separated from user price.

Avoid:

- permanent launch discount;
- fake crossed-out price;
- membership discount before membership value exists.

---

# 7. Experiment decision

After each offer:

- PASS — demand + fulfillment + economics justify next cohort;
- ITERATE — value exists but pricing/format is weak;
- HOLD — sample too small / invalid;
- FAIL — insufficient demand at viable terms;
- INVALID — truth/payment/measurement compromised.

---

# Final rule

> **PRICE TESTS THE VALUE OBJECT. IT MUST NOT SUBSTITUTE FOR DEFINING THE VALUE OBJECT.**
