# DEMENTOR CLUB — OPERATING MODEL / EDITORIAL CAPACITY / GOVERNANCE v1

Status: **DRAFT / OPERATING MODEL CANDIDATE**  
Updated: **2026-09-15**

## Purpose

Define how Dementor can sustain a Thing-first Program without turning into a content factory or depending on one person for every decision.

---

# 1. Operating principle

> **PROGRAM QUALITY IS A CAPACITY PROBLEM AS MUCH AS AN EDITORIAL PROBLEM.**

The system needs enough capacity to:

- notice;
- reframe;
- make;
- release;
- program;
- distribute;
- fulfill;
- measure;
- close loops.

Do not set cadence first and then force production to fill it.

---

# 2. Core operating roles

One person may hold multiple roles early, but responsibilities must be explicit.

## Product / semantic owner

Owns:

- 01–15 coherence;
- Thing / Program / Contribution boundaries;
- product-level decisions.

## Editorial / Programming owner

Owns:

- what matters now;
- Programming Moments;
- sequence / resurfacing;
- editorial disposition.

## Thing owner / producer

Owns one Thing or bounded body of work:

- source truth;
- making;
- Release readiness;
- factual updates.

## Distribution owner

Owns:

- channel fit;
- message delivery;
- exact destination;
- attribution context.

## Fulfillment owner

Required for paid/live/physical offers.

Owns:

- delivery;
- support;
- failure handling;
- capacity.

## Measurement owner

Owns:

- sample integrity;
- Product Health review;
- experiment evidence;
- no overclaiming.

## Commercial / finance owner

Owns:

- offer terms;
- cost model;
- payment readiness;
- experiment P&L.

---

# 3. Decision rights

### Source truth

Thing owner / operational source.

### Is this a Thing?

Product/semantic authority + editorial review.

### Is it in Current Program now?

Programming owner.

### Can it be publicly distributed?

Programming + Distribution, subject to truth/access constraints.

### Can it be sold?

Commercial readiness + fulfillment + legal/payment gate.

### Can it be called successful?

Measurement evidence, not owner enthusiasm.

---

# 4. Editorial pipeline

```text
OBSERVATION / SOURCE CHANGE
→ EDITORIAL LOOK
→ THING / UPDATE / CONTRIBUTION / NO ACTION
→ MAKING
→ RELEASE TRUTH
→ PROGRAMMING DECISION
→ DISTRIBUTION
→ EXPERIENCE
→ HISTORY / CONTINUATION / CLOSURE
```

Each stage must be able to end without forcing the next one.

---

# 5. Capacity units

Do not count only “posts” or “releases”.

Track effort by operating unit:

- editorial review;
- new Thing production;
- Thing maintenance/update;
- Event/live delivery;
- Course/tool maintenance;
- contribution review;
- distribution package;
- measurement/review;
- commercial fulfillment.

Use actual hours or rough effort bands initially.

---

# 6. Sustainable cadence

Do not commit to daily/weekly output quotas yet.

Determine cadence from observed capacity:

```text
AVAILABLE EDITORIAL CAPACITY
- MAINTENANCE / OPERATIONS
- FULFILLMENT
= NET MAKING / PROGRAMMING CAPACITY
```

Then set a Program rhythm that can be fulfilled without filler.

Healthy outcome may be:

- fewer Programming Moments;
- higher Thing quality;
- more resurfacing / continuation;
- less forced novelty.

---

# 7. Bottleneck review

Weekly, identify the dominant bottleneck:

- source truth;
- editorial decision;
- making capacity;
- design/dev;
- author dependency;
- fulfillment;
- legal/payment;
- distribution;
- measurement.

Do not solve a production bottleneck by adding more incoming Contributions.

---

# 8. Founder / key-person risk

Reduce concentration through:

- explicit editorial criteria;
- multiple Thing owners;
- documented Programming decisions;
- body of work for multiple Dementors;
- repeatable review templates;
- source-truth ownership.

Do not reduce distinctiveness by committee-writing every Thing.

---

# 9. Contribution operating model

Contribution requires service-level clarity, not a promise of publication.

Define:

- acknowledgment owner;
- review queue;
- disposition owner;
- closure expectation;
- provenance preservation.

Do not accept unlimited contribution volume without review capacity.

---

# 10. Live / Event operating model

Before opening participation/sales define:

- capacity;
- facilitator/host;
- venue/tooling;
- registration owner;
- cancellation/failure policy;
- participant communications;
- post-event History / continuation;
- actual cost base.

---

# 11. Operating reviews

## Weekly

- Current Program;
- blockers;
- upcoming releases / events;
- contribution closure;
- delivery issues;
- data validity.

## Monthly

- Program quality;
- Thing→Thing / Return;
- capacity usage;
- commercial experiment status;
- bottleneck trend.

## Quarterly

- segment learning;
- operating model changes;
- role/capacity needs;
- kill/continue decisions for formats.

---

# 12. Hiring / contractor gate

Add capacity when a repeated bottleneck is proven.

Examples:

- recurring video bottleneck → production support;
- contribution backlog → editorial operations;
- live fulfillment demand → facilitator/producer;
- commercial admin load → operations support.

Do not hire for hypothetical scale before the value loop exists.

---

# Final rule

> **THE OPERATING MODEL EXISTS TO PROTECT EDITORIAL VALUE FROM BOTH CHAOS AND CONTENT-FACTORY PRESSURE.**
