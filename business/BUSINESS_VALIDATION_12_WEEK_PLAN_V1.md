# DEMENTOR CLUB — BUSINESS VALIDATION 12-WEEK PLAN v1

Status: **WORKING PLAN / BUSINESS VALIDATION PROGRAM**  
Updated: **2026-09-15**

## Purpose

Turn Business Analysis Pack decisions into a bounded execution program.

Goal for 12 weeks:

> **Prove whether at least one external segment repeatedly receives value from Dementor, continues to another Thing, returns, and shows enough commercial intent to justify one small paid experiment.**

This plan does not authorize production deploy, payment, legal claims, paid acquisition scale or subscription.

---

# 0. Program outcomes

At the end of 12 weeks we must be able to answer:

1. Which segment shows the strongest external value signal?
2. Which Thing / value object works best as entry?
3. Does Thing→Thing continuation occur?
4. Does meaningful Return occur?
5. Which channel carries highest-quality demand?
6. Is there one concrete paid hypothesis worth testing?
7. What does delivery actually cost in time/money?
8. Is the current operating model sustainable?
9. What remains blocked by legal/commercial setup?

Acceptable end states:

- **PASS TO PAID TEST**;
- **ITERATE PRODUCT/GTM**;
- **HOLD — insufficient evidence**;
- **FAIL current segment hypothesis**.

Do not force a positive conclusion.

# 2. Week 1 — Measurement integrity + experiment setup

### Goal

Make external evidence trustworthy before generating more traffic.

### Work

- verify internal/test traffic separation;
- verify QA/smoke activity exclusion;
- define experience-start for each selected Thing;
- define continuation events/derived logic;
- define expected return window per Thing/Program moment;
- create experiment registry;
- start operating-capacity log.

### Experiment registry fields

```text
experiment_id
segment_hypothesis
thing
channel
message
entry_object
experience_definition
continuation_definition
expected_return_window
sample_type
cost_or_effort
owner
status
```

### Gate

No external comparison until sample integrity is good enough to distinguish:

- internal/test;
- warm network;
- partner audience;
- external/cold where available.

---

# 3. Week 2 — Message / entry preparation

### Goal

Prepare truthful acquisition without changing Product authority.

### Prepare 3 message modes

For the same underlying Thing where suitable:

1. **OBSERVATION-FIRST**;
2. **UTILITY-FIRST**;
3. **THING-DEMO-FIRST**.

Do not test organization-first Club explanation as default.

### Channels

Prepare:

- private share;
- Telegram owned;
- one social/editorial surface;
- one partner/community placement candidate.

### Sample target

Enough small cells to learn, not to claim statistical certainty.

Prefer multiple independent cohorts over one large founder-network blast.

### Gate

Every message must land on exact Entry Object.

---

# 4. Weeks 3–4 — External value test A

### Goal

Prove `attention → experience` outside internal use.

### Run

S1 and S2 through at least two different acquisition contexts each where feasible.

### Collect

Quantitative:

- qualified entries;
- experience starts / meaningful use;
- experience completion proxy where Form permits;
- Thing→Thing continuation;
- share intent/action where observable.

Qualitative:

- what they thought the Thing was;
- what was worth attention;
- what confused them;
- what they wanted next;
- whether they described the Club/system or the Thing/value.

### Decision after Week 4

Per Thing × segment:

- PASS;
- ITERATE;
- HOLD;
- FAIL;
- INVALID.

Do not optimize traffic volume yet.

---

# 5. Weeks 5–6 — Continuation + Return test

### Goal

Determine whether Dementor behaves like a Program rather than isolated Things.

### Work

For strongest Week 3–4 combinations:

- improve one natural next Thing;
- preserve truthful closure where no continuation exists;
- run another Programming Moment / reason to return;
- observe direct/owned return.

### Evidence

- source Thing experience;
- continuation chosen;
- target Thing experience;
- return in expected window;
- return payoff.

### Business question

> Does the person want more Dementor, or did they only like one isolated artifact?

Both answers are valid evidence.

### Gate D review

At Week 6 evaluate `Proof of Return` by segment.

If no segment shows a return signal:

- do not proceed toward recurring hypotheses;
- decide whether issue is Program cadence, continuation relevance, or one-off-only value.

# 6. Week 7 — Segment selection review

### Goal

Choose where to concentrate the remaining cycle.

### Compare S1 vs S2 on

- experience quality;
- continuation;
- return;
- share;
- acquisition effort;
- qualitative fit;
- potential paid adjacency;
- operating burden.

### Output

One of:

- **PRIMARY WORKING SEGMENT = S1**;
- **PRIMARY WORKING SEGMENT = S2**;
- **BOTH remain distinct and useful**;
- **SEGMENT MODEL INVALID / redesign needed**.

Do not choose by vanity size.

# 8. Week 9 — Commercial-intent probe

### Goal

Measure whether next-value language survives contact with a literal offer.

### If payment is NOT ready

Use only truthful non-payment commitment:

- waitlist;
- application/request;
- reservation interest;
- explicit request for notification;
- interview around exact offer terms.

Do not label this willingness-to-pay proof.

### If payment readiness IS approved

A small real commitment/deposit/payment test may be designed separately under BA-07 gates.

### Evidence

Track:

- offer views;
- explicit interest;
- commitment;
- objections;
- price reaction;
- fulfillment questions;
- segment differences.

# 9. Week 10 — Cost / capacity truth

### Goal

Stop treating founder/team labor as free.

### Compile 8–10 weeks of actual operating effort

By:

- editorial review;
- Thing maintenance;
- programming;
- distribution;
- measurement;
- development support;
- user support;
- commercial preparation.

### Build first real capacity view

```text
available_hours

- maintenance
- fulfillment

```

### For selected paid hypothesis

Estimate:

- fixed prep cost;
- variable fulfillment;
- maximum quality-preserving capacity;
- break-even if applicable.

### Decision

Determine whether the offer is operationally plausible before selling it.

# 11. Week 12 — Investment decision

End the cycle with exactly one portfolio decision.

## Decision A — PASS TO SMALL PAID TEST

Requirements:

- primary segment credible;
- experience proven;
- continuation/return signal exists;
- one concrete value object has real intent;
- delivery/capacity plausible;
- legal/payment work can be resolved.

Next:

- BA-07 readiness;
- one paid cohort;
- no paid acquisition scale.

## Decision B — ITERATE PRODUCT / PROGRAM

Use when:

- experience works but continuation/return weak;
- user value is clear but Program sequence is weak.

Next:

- improve Program/Thing continuity;
- no commerce push.

## Decision C — ITERATE GTM / SEGMENT

Use when:

- experienced users value the Thing;
- reach/message/source fit is weak.

Next:

- keep product;
- change segment/channel framing.

## Decision D — HOLD

Use when sample/data validity is insufficient.

## Decision E — FAIL CURRENT HYPOTHESIS

Use when repeated external cohorts do not show meaningful experience/value.

Do not hide FAIL by launching Membership or discounts.

# 12. Numeric discipline

This plan deliberately does not invent universal conversion targets.

During the first cycle:

- establish baselines;
- compare cohorts consistently;
- identify repeated directionality;
- separate sample quality from metric value.

After a real baseline exists, numeric targets may be proposed for the next cycle.

### Minimum qualitative discipline

No major decision should rest on:

- one person;
- one viral post;
- founder friends only;
- internal/admin usage;
- one unusually successful Event;
- likes/comments without experience evidence.

---

# 13. Weekly operating rhythm

## Monday — Program / experiment review

- current Programming Moments;
- experiments live this week;
- truth/access blockers;
- owner assignment.

## Midweek — data quality / qualitative review

- sample contamination;
- unexpected behavior;
- broken routes/events.

## Friday — learning decision

For each active experiment:

- KEEP RUNNING;
- ITERATE;
- STOP;
- INVALIDATE.

No experiment should drift indefinitely.
